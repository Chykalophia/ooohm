# OOOhm: notes for coding agents

OOOhm (Out Of Office, Holiday Manager) is a leave tracker for small teams. The v1 scope lives in the
"OOOhm — v1 Scope" doc, and the work is tracked in ClickUp (Internal Projects → OOOhm, tasks M0–M7).
Work one milestone at a time and keep each PR to a single milestone.

## Product rules (don't break these)

- **The UI stays calm.** Use one accent color (teal in the default Classic theme), keep whitespace generous, and keep each screen to one main action. If a screen needs explaining, it's wrong.
- **Themes are company-wide; light or dark is per person.** An admin picks the theme, an optional accent color and the corner style (Admin → Appearance); people can't override it. Each person picks a colour mode (light, dark, automatic), which applies where the theme has a dark version (Classic, for now). Style screens with the theme tokens (`bg-accent`, `text-accent-ink`, `bg-surface`, `border-border`, …), never fixed brand colors, so every theme works. Use `text-accent-ink`, not `text-accent`, for accent-colored text.
- **Access is invite-only.** Neither magic links nor Google sign-in may create users. Admins (or the seed) create them.
- **The allowance policy is pluggable.** v1 ships only `annual_calendar_year`: a flat yearly allowance per leave type that resets Jan 1. Carryover is set per leave type and is OFF by default. A leave type's default can be replaced per department, level or both by allowance rules (`src/modules/balances/domain/allowance-rules.ts`; the most specific wins); every balance reads defaults through `loadAllowanceDefaults` (`@/modules/balances`, the module's only read path), never `leaveType.defaultAllowanceDays` directly (`tests/architecture/default-allowance.test.ts` lists where the field may be read; the balance code's read of the setting is `src/shared/lib/db/leave-type-allowances.ts`).
- **Approvals:** one approver per person: their manager, else their department's manager (optional, set in Admin → Departments), else an admin. `user.can_self_approve` auto-approves that user's own requests. Routing is loaded in one place (`loadApprovalContexts`, `src/modules/approvals/infrastructure/drizzle-approval-context.reader.ts`, the `ApprovalContextReader` port); the rule is `src/modules/approvals/domain/approver-for.ts`.
- **Whose time off someone sees is one rule:** `calendarScopeFor` (`src/shared/kernel/calendar-visibility.ts`), loaded only by the calendar module (`loadCalendarScope` / `scopeOf` from `@/modules/calendar`). Admins see everyone; employees follow Admin → Company's colleague visibility; with department scoping on (off by default) everyone but admins is kept to their own departments. Any new screen that shows colleagues' leave filters by that scope.
- **Integrations go through `events_outbox`.** Write a domain event in the same transaction as every state change. No adapters ship in v1.
- **Audit everything.** Every request decision and every balance change writes an `audit_log` row, naming who or what made it (a person, a person through a sync or import, their API key, or a system process). Nothing is anonymous.
- **Day counts are numeric with one decimal place** (half days = 0.5). Weekends and company holidays never count.

## Architecture standard (in transition)

OOOhm is moving to Chykalophia's *SaaS Layered Architecture Reference*: a modular monolith of feature modules
(`src/modules/<m>/{ui,application,domain,infrastructure,index.ts}`), with Tier 3 for leave, approvals and balances
and Tier 2 for everything else. Read `ARCHITECTURE.md` first. The plan is in `docs/architecture-plan/` (phases
A0–A8) and the decisions are in `docs/adr/`.

- Architecture PRs keep behaviour unchanged and cover one phase each. Never mix them with feature work.
- A move is a rename: moves, import rewrites and a temporary re-export, nothing else.
- New code goes into `src/modules/<m>` when that module exists. Otherwise it follows the layout below.
- Write the failing test or fitness check first. The existing integration and email snapshot suites are the safety
  net, so don't edit their assertions in a move.
- Before a PR, check: is the code in the right layer? Is auth inside the action pipeline and the use case? Is a DTO
  returned, not a row? Is the dependency direction allowed? Does the change need an ADR?

## Stack and commands

Next.js 16 (App Router, `output: "standalone"`, Cache Components **off**), TypeScript, Postgres + Drizzle,
Better Auth (magic link + optional Google), Tailwind v4, pnpm. Runs on any Postgres 15+ or embedded PGlite, with Docker,
on Vercel, or on one machine (docs/hosting.md): never assume a host.

```bash
pnpm dev            # local dev (needs Postgres + .env)
pnpm typecheck      # tsc --noEmit over the whole repo: strict plus noUncheckedIndexedAccess, exactOptionalPropertyTypes, noImplicitOverride, noFallthroughCasesInSwitch (tsconfig.json); in tests, narrow rows with first/at/take/present (tests/support/present.ts)
pnpm lint
pnpm db:generate    # after editing src/db/schema.ts — commit the generated SQL in drizzle/
pnpm db:check-drift # fails if src/db/schema.ts has a change no committed migration makes (ADR-0011; CI runs it)
pnpm db:roles       # idempotent: creates/repairs the owner and app roles (deploy/db-roles.sql)
pnpm db:migrate     # as the owner (DATABASE_ADMIN_URL), then refreshes the app role's grants
pnpm db:seed        # idempotent; uses SEED_ADMIN_EMAIL; as the owner
pnpm job:rollover   # idempotent year rollover (carryover + new-year allowances)
pnpm worker         # outbox worker: webhooks, adapter deliveries, daily rollover + retention
pnpm import:timeoff -- --file <x.sqlite> --company <id> --actor <admin email> [--apply]   # one-time TimeOff import (dry run by default)
pnpm test           # unit tests + tests/architecture + tests/contracts (no database)
pnpm test:components # component tests in tests/components (React Testing Library on jsdom; docs/architecture.md#testing)
pnpm arch           # dependency rules (.dependency-cruiser.cjs); fails on any violation (there is no baseline)
pnpm madge          # import cycles (none allowed)
pnpm test:integration  # service tests; set TEST_DATABASE_URL (see docs/architecture.md#testing)
pnpm test:integration:embedded  # the same on embedded PGlite (no server); keep both green
pnpm start:embedded # after pnpm build: migrate, seed and serve on embedded PGlite (docs/hosting.md)
pnpm test:e2e       # after pnpm build: Playwright journeys on pnpm start:embedded (Chromium; docs/architecture.md#testing)
docker compose up   # full stack: db, migrate+seed, app, mailpit (http://localhost:8025)
```

## Layout

Layered; dependencies point downward only. Full rules in `docs/architecture.md`.

- `src/app/**`: presentation. Thin pages and server actions. Signed-in pages open with `requireMemberPage()` / `requireAdminPage()` and render inside `AppPage` / `AdminShell` (sign-in and route handlers are the exceptions; the API has its own entry below); actions are a zod schema and one module call through `runFormAction` / `runStateAction`, or `runActionThenGo` to redirect after (`src/app/_lib/server-action.ts`), in an `actions.ts` beside the route that uses them. Pages stay thin: shaping goes in a module's `ui/` presenter, markup in components beside the route. Pages and actions import only module indexes, `src/app`, `src/components`, the shared kernel, `Result`, search params and pure `src/lib` helpers (`pages-and-actions-through-modules`, `pnpm arch`). ESLint's size limits are errors (`sizeLimits` in `eslint.config.mjs`, with its short allow-list). No Drizzle here. Route-specific components sit beside their route.
- `src/app/_lib/**`: the presentation layer's helpers: page loaders (`page-context.ts`), the server action pipeline (`action-pipeline.ts`, wired in `server-action.ts`, with a per-person rate limit, `ACTION_RATE_LIMIT`), shared form field schemas, `runActionWith` messages, input schemas, the app's background tick.
- `src/components/**`: shared UI, by kind (`ui`, `forms`, `layout`, `navigation`, `leave`). Components render props; they never load data or import `src/app` or `src/server` (lint enforces it). Style controls with the recipes in `src/components/ui/styles.ts`, not new Tailwind strings. Colours are theme tokens from `src/app/globals.css` (light and dark in one `light-dark()` value); lint refuses palette classes and `dark:`. Lists that grow with use are paged with `readPage` + `Pager`, never capped. See docs/architecture.md#presentation.
- `src/app/admin/**`: the admin screens. Pages start with `requireAdminPage()` (404 for non-admins) and render in `AdminShell`; actions go through `adminAction()`. The services check the role again (`assertCanAdminister`), so never rely on the page alone.
- `src/modules/<m>/**`: feature modules (`src/modules/README.md`, ADR-0009): `application/{use-cases,queries,policies.ts,dto.ts,schemas.ts}`, `domain/`, `infrastructure/` (repositories), `ui/` (presenters), `index.ts`, `README.md`. Everything outside a module imports `@/modules/<m>` only; use cases and queries that can fail return a `ServiceResult`, and the index never exports a row or anything from `infrastructure/` (`pnpm arch`, `tests/architecture`). So far: `reports` (the leave report and its CSV), `organisation` (company settings and appearance, departments, levels and the leave type catalog; it imports no other module), `notifications` (every email and Admin → Emails), `audit` (the audit log viewer), `integrations` (webhooks, API keys and the REST API's reads, adapters, the outbox jobs), `import` (the CLI-only TimeOff import), `holidays` (Admin → Holidays; edits recount leave through `@/modules/leave`), `calendar` (the month, year and Who's out views, feed links, the calendar scope loader and the calendar reads other modules use; it imports no module but organisation), `leave` (Tier 3: submitting, cancelling, adding and removing leave for someone, recounts, "Your requests", the dashboard and the API's leave list; its README covers the aggregate, ports, fakes and repository contract) and `balances` (Tier 3: the allowance policy as a Strategy with its registry, balances and the live preview, allowance rules, the admin allowance editor and the year rollover), `people` (Admin → People: invite, edit, deactivate, delete with its grace period and scheduled scrub, the records export and CSV import; the teammate page; a person's own account; the member directory other modules read is `src/shared/lib/db/members.ts`, so nothing below people imports it), and `approvals` (Tier 3: deciding requests, the Approvals page, approve from the email, re-routing pending requests after an admin change; it implements leave's `ApprovalRouter`, handed over by `wireModules` in `src/server/wiring.ts`, which every composition root calls, so leave never imports approvals).
- Use cases live in their module's `application/` (there is no `src/server/services`, and no `src/server/repositories`: `tests/architecture/no-old-layers.test.ts`). They own transactions, data-dependent authorization, `recordLeaveChange`/`recordChange` for every state change, and email via `commitThenNotify` (`@/modules/notifications`; after commit, never throws), returning notifications from that module (never rendering mail themselves). Admin use cases check `assertActiveAdmin` and record changes with `recordAdminChange` (`src/shared/lib/admin-access.ts`), and take `lockCompany` (`src/shared/lib/db/company-lock.ts`) first when a rule spans several people. A change that spans modules lives in the module that can import the others: `updateCompanySettings` (leave) runs organisation's settings step with the recount, and `setDepartmentManager` (approvals) runs organisation's department step with the re-route, so organisation never imports leave, approvals or notifications.
- `src/shared/**`: what every module shares. `kernel/` holds pure rules (`ids` and `uuid`, `admin-permissions` with `assertCanAdminister`, `coverage-limit`, `addDays` in `day-amounts.ts`, the allowance policy keys in `allowance-policy-keys.ts`, the name and email normalizers in `names.ts`, `personLabel` / `teamLabel` in `person-label.ts`, the CSV helpers in `csv.ts`, and the leave range and day-counting rules in `leave-range.ts` and `leave-days.ts`); `lib/` holds `result.ts` (`ServiceResult`), `unit-of-work.ts` (`inTransaction`), `admin-access.ts` and `db/` (`recordChange` in `change-log.ts`, `keysetPage` in `keyset.ts`, driver `errors.ts`, the company locks in `company-lock.ts`, the company columns in `company-columns.ts`, creating a company in `company-creation.ts` (install and import), the leave request reads modules below leave need in `leave-requests.ts`, the leave type allowance settings in `leave-type-allowances.ts`, the member directory in `members.ts`, and the jobs' reads in `scheduled-jobs.ts`, `retention.ts` and `health.ts`: repository code, held to the repository rules). Every outbox write goes through `recordChange` (ADR-0010).
- `src/server/jobs/**`: the background tick (`background-tick.ts`), the daily jobs (`scheduled-jobs.ts`), retention and the health check. `src/server/identity/**`: the first install (`install.ts`).
- `src/modules/notifications/**`: every email a change sends. In `application/`, `catalog.ts` lists the notification types, `templates/` the pure renderers (lint keeps them pure), `send.ts` the after-commit sender and `commit-then-notify.ts` the one way services send mail. Add an email as a template plus a catalog entry (with its editable copy: defaults, variables, sample); `tests/unit/email-output.test.ts` pins every email's output. Admins change an email's subject and message in Admin → Emails (`saveEmailCopy`, `resetEmailCopy`, `getEmailForAdmin`, `previewEmail`); everything else in it stays fixed.
- `src/modules/audit/**`: the read-only audit log viewer (`getAuditLog`), a person's history for their records export, and the count the invite and import rate limits read. Admins only (`canViewAuditLog`).
- `src/server/integrations/**`: the adapter seam (`Adapter`, `adapterRegistry`), the port `ServiceContext` names; `installed.ts` lists adapters (none in v1). No database access: the integrations module writes what adapters return. The envelope they receive is `src/shared/kernel/event-envelope.ts`.
- `src/modules/integrations/**`: webhooks, API keys, the REST API's reads, adapters and their syncs, and the outbox jobs (`dispatchOutboxBatch`, `deliverDueWebhooks`, `deliverDueAdapterEvents`) the background tick runs. `application/contracts.ts` holds the zod contract of every event in docs/api.md; `tests/contracts/` checks the code and recorded samples against it, and the signature vectors. Admins only (`canManageWebhooks`, `canManageApiKeys`, `canManageAdapters`); DTOs never hold a key's hash or a webhook secret.
- `src/modules/import/**`: the one-time TimeOff import, CLI-only (lint keeps it out of `src/app`). `infrastructure/` reads TimeOff's SQLite file into `domain/timeoff` records (files only); `domain/timeoff/mapping.ts` plans it one entity at a time; `application/import-timeoff.ts` owns the transaction and applies the plan in steps. See `docs/import.md`.
- `deploy/`: the production compose file, Caddyfile, backup/restore scripts and systemd timer. Runbook: `docs/deploy.md`.
- `src/app/api/v1/**`: the REST API. Routes are one line through `_lib/api-get.ts` → `_lib/handler.ts` (auth, rate limits, errors); keep `_lib/openapi.ts` in sync (a test checks).
- Pure rules (no I/O, Next, Drizzle or env) live in a module's `domain/`, or in `src/shared/kernel/` when client components, the schema, `src/lib` or several modules use them. Leave's status machine, overlap and coverage rules are in `src/modules/leave/domain/`, the allowance policy and rules in `src/modules/balances/domain/`, the audit log's labels in `src/modules/audit/domain/audit.ts`; the kernel holds `DomainError` (`errors.ts`), the event catalog (`events.ts`), `ChangeSource`, `Actor`, calendar dates, paging and the range and day-counting rules. There is no `src/domain` (`tests/architecture/no-old-layers.test.ts`).
- `src/server/context.ts` / `src/server/runtime.ts`: the injected `ServiceContext` type and the app's composition root.
- `src/db/config.ts` / `src/db/connect.ts`: the one place a database is chosen and opened (Postgres with pooler detection, or embedded PGlite with its directory lock). Scripts, the worker and tests open it there too. Postgres is two roles (ADR-0006, docs/deploy.md#database-roles): the app, the cron route, the worker and the rollover job use the app role (`DATABASE_URL`: rows only, no DDL, `audit_log` insert-only); migrate, seed and the TimeOff import use the owner (`DATABASE_ADMIN_URL`, required on Postgres), opened only by `src/server/admin/db.ts`, which nothing else in `src` may import. Embedded PGlite keeps one data directory; its app handle acts as the `ooohm_app` role. A new table needs no grants: default privileges and `pnpm db:migrate`'s re-grant cover it. Never give the app a way to change audit rows other than the owner's functions in `drizzle/0030`. Raw `execute()` results differ by driver: use the query builder, or `executeRows` (`src/db/rows.ts`).
- **Row-level security** (ADR-0004, `drizzle/0031_row_level_security.sql`): every table with `company_id`, and the children scoped through it (`allowances`, `leave_request_days`, `session`, `account`, `passkey`), shows and takes only the rows of the transaction's company (`app.company_id`), and nothing without one. A new tenant table gets `ENABLE` and `FORCE ROW LEVEL SECURITY`, the four `<table>_tenant_*` policies on `public.ooohm_tenant()` and the `<table>_owner` policy in the same migration (`tests/architecture/row-level-security.test.ts` fails otherwise; add its rows to `tests/integration/rls.test.ts`). Read and write tenant rows through `forTenant(ctx, companyId)` (`src/shared/lib/tenant.ts`) with the actor's or API key's company, never one from input; `inTransaction`, `commitThenNotify` and the Tier 3 compositions scope themselves. A bare `ctx.db` sees no tenant rows. A read that must find the company first (a key or token hash, a signed link, a job's queue) is a narrow `SECURITY DEFINER` function with `search_path` pinned, called from `src/shared/lib/db/pre-tenant.ts` and listed in the fitness test; never a bypass setting or `BYPASSRLS`. Better Auth reads its tables through the owner's views (`src/db/auth-schema.ts`, for `src/lib/auth.ts` only).
- `src/db/schema.ts`: every table. Better Auth's tables (`user`, `session`, `account`, `verification`) live here too.
- `src/lib/auth.ts`: Better Auth config, `issueSignInLink()` (invite links, wired into `ServiceContext`), `requireUser()` and `requireActor()`, the entry points for pages and actions (`currentUser()` for route handlers, which answer 401 instead of redirecting).
- `src/lib/env.ts`: validated env vars. Add new ones here, in `.env.example`, and in `docker-compose.yml`. Values are trimmed on read. The owner's `DATABASE_ADMIN_URL` (and `DATABASE_SUPERUSER_URL`, `OOOHM_DB_*` for `pnpm db:roles`) are the exception: read only in `src/server/admin/db.ts`, never in the app's or the worker's environment.
- Background work is one function, `runTick` (`src/server/jobs/background-tick.ts`), run by the worker, `/api/cron/tick`, the inline after-change tick (`ctx.wake`, via the `inTransaction` / `commitThenNotify` seam: `src/shared/lib/unit-of-work.ts` and `@/modules/notifications`) or embedded mode's timer (`src/instrumentation-node.ts`). A service that records changes opens its transaction with `inTransaction(ctx, companyId, ...)` (or `commitThenNotify`), never `ctx.db.transaction`, so inline mode sees its events and row-level security its company.
- `scripts/*.mts`: the database roles (`pnpm db:roles`), migrate, seed and the year rollover (`pnpm job:rollover`), run in that order by the `migrate` compose service; and the outbox worker (`pnpm worker`, the `worker` service), which delivers webhooks and runs the daily jobs. The worker reads `src/lib/worker-env.ts`, never `env.ts`. `import-timeoff.mts` is the one-time TimeOff importer.
- `site/`: the marketing landing page, a static site deployed apart from the app (no build step). `site/demo/` records its videos from the real app with demo data. See `site/README.md`.
- `docs/guide/`: the product guide, screen by screen, with every setting and email; `site/docs/` is built from it (`node site/demo/build-docs.mjs`) and its screenshots come from `site/demo/docs-screens.mjs`. Update the page (and its shot) with any change to a screen, a setting or an email. See `site/README.md`.
- `docs/api.md`: the public integration reference (auth, endpoints, events and payloads, webhooks, signatures). Update it with any event or API change.
- `tests/unit/**` (`pnpm test`) and `tests/integration/**` (`pnpm test:integration`, needs `TEST_DATABASE_URL`; fresh database per file). Both run under `--conditions=react-server` so `server-only` modules load. `tests/components/**` (`pnpm test:components`) runs client components on jsdom without that condition; `tests/components/setup.ts` stubs `next/navigation` and, per file, the server actions a component imports. Every new exported function of a module index, service, job or identity file, and every new `/api/v1` route, needs a cross-company case in `tests/integration/tenancy.test.ts` or an exemption with its reason in `tests/support/tenancy-coverage.ts` (an architecture test fails otherwise).
